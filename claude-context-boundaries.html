01一个核心区分：注入面 vs 可达面

整份文档最重要的一条。把这两件事混为一谈，会产生错误的"隔离感"。

Project 隔离的是"自动想起"，不是"能不能查到"。记忆不会跨项目注入——这条成立。但只要主动调工具，跨项目的内容全都拿得到。

这个区分有实际后果：如果你原本指望把敏感内容放进单独的 project 就能与其他会话隔离开，那是不成立的。目前真正做到不留痕的只有 Chat 侧的隐身对话（不写入历史、不进记忆），Cowork 这边没有对等机制。

02三条互不相通的上下文栈

Claude Code 不是第三种模式，是完全另一套状态系统——共用的只有账号、额度和硬盘。

CLAUDE.md / auto memory无关无关这是它的全部

想让 Claude Code 的上下文跟着你走，只有一个办法：把 CLAUDE.md 放进被 Git 或云盘同步的目录。它在 Claude Code 里扮演的角色，正好等于 Project 指令在 Chat / Cowork 里的角色。

03Instruction 与 Memory 的关系

一个是每次开局必读的合同，一个是可能被想起的笔记。

InstructionMemory
谁来写你手写（Folder 指令 Claude 可自更新）Claude 边聊边自动写
回答什么该怎么做 —— 口径、格式、禁忌你是谁、发生过什么 —— 角色、偏好、项目进展
是否保证生效是，每次开局注入否，Claude 觉得相关才调
跨 Chat / CoworkProject 指令通完全不通
跨 Claude Code不通，它只读 CLAUDE.md不通
你怎么改直接编辑对应层级的指令框Settings › Memory 里查看 / 编辑 / 删除
凡是"必须每次都生效"的东西，写进指令，不要指望记忆。

04Project 的真实作用

同一个 Project 里，Chat 会话和 Cowork 会话共享的是指令与知识库，不是记忆。

记忆不通，为什么还要放同一个 Project？图的就是共享层：Project 指令 + 知识库，两种会话都读得到，而且是确定性读到。Project 让你把"希望 Claude 每次都知道的东西"，从不可靠的记忆里搬进可靠的指令和知识库里。

05实例：多项目下的可达范围

上半层隔离成立，下半层隔离不成立——同一批项目，两种结论。（项目名已脱敏）

这件事的实际后果：如果你把不同性质的内容（比如健康记录和财务分析）分到不同 project，指望它们互相看不见——在记忆层面确实互不串门，但任何一个 Cowork 会话，包括随手开的"帮我整理下载文件夹"，都能把两边逐字稿一起读出来。

06项目文件夹：指定 vs 未指定

两种路由对应两种完全不同的知识来源与能力边界。

未指定（纯云端）指定了文件夹
路由/cowork/project/…/space/…
Web 与手机正常打开空白页，桌面独占
知识来源上传的 Files（有容量条）磁盘文件夹（无上限）
Claude 写回不写回，产出要手动加进项目直接改文件，产出自动落盘
版本管理重传一份新的走原有流程（Git、云盘同步…）
外部 agent读不到读得到，就是普通文件夹
没有所谓的"项目默认目录"。桌面端 用户目录\Claude\ 全量扫过，只有 Scheduled\（定时任务）和 Artifacts\（live artifacts），没有任何项目文件夹。那是 Claude 放自己产物的地方。项目只有两种状态：绑一个你选的路径，或者根本没有本地文件夹。

另一个发现：上传到云端项目的文件会在本地留一份只读镜像，路径形如 AppData\…\.project-cache\<项目ID>\docs\，原始 .docx 被转成 .md。所以 Cowork 读云端知识库不是实时调 API，是读这份镜像——这也解释了"读得到但改不了"。

一句话选型：指定文件夹换来的是"文件流"，不指定换来的是"跨端"。有真实文件要反复迭代 → 指定；纯对话推演、随时随地要能开 → 不指定。

08外部 agent 的边界

Codex、Cursor 等：唯一实际交集是你电脑上的本地文件夹。

想做 Claude + 外部 agent 协作，交接点只能是磁盘上的文件。反过来 Cowork 也能读外部 agent 的工作目录——实测在 Codex 的默认输出目录下看到了完整的会话产出。

09实测记录与更正日志

本文档的结论来自实机验证，与早期推断冲突的地方一并记录。

实测证据

  • 实测跨项目读取成立。在一个不属于任何 project 的 Cowork 会话里，一次调用读到了 22 个 Cowork 会话的完整逐字稿，横跨五个不同项目。session_info 返回扁平列表，不含 project 字段。
  • 实测Cowork 能读 Chat，但走浏览器。session_info 返回 0 条 chat；通过浏览器扩展以已登录身份打开 claude.ai/chat/…，可读任意对话全文。权限来源是登录态，不是 Claude 内部数据通道——扩展没连时这扇门就是关的。
  • 实测账户级指令覆盖 Cowork。Settings › General 的「Instructions for Claude」字段说明原文写着 "across chats and Cowork"。Web 端设置里没有 Cowork 栏（搜索返回 No matching settings），Cowork 全局指令只存在于桌面应用。
  • 实测无项目默认目录。用户目录下的 Claude\ 只有 Scheduled\ 与 Artifacts\，无任何项目文件夹。
  • 实测云端项目文件有本地镜像。.project-cache\<项目ID>\docs\ 下存着 .docx 转换后的 .md。
  • 实测Claude Code 状态完全本地。~/.claude/ 下是会话历史与凭据，按工作目录分组；没有 CLAUDE.md 就等于每次白纸开局。
  • 实测folder-bound 项目桌面独占。/space/… 路由在浏览器里渲染为空白页。
  • 实测Claude 无法操作自己的应用窗口。computer-use 明确拒绝授予对 Claude 自身界面的控制权——否则它就能改自己的权限与设置。

更正日志

  • 更正"项目之间互不可读"是错的。早期图把"记忆隔离"画成了"读取隔离"。正确表述：Project 隔离的是自动注入，不是可达性。
  • 更正"Chat Project 与 Cowork Project 是两个独立对象"已过时。较新文档明确：从同一个 Project 既能开 chat 也能开 Cowork 会话，共用同一份项目知识。早期那张"一次性导入 / 链接"的单向箭头图是过渡期产物。
  • 更正"Profile 指令可能不覆盖 Cowork"推断错误。该字段说明原文即写明覆盖 Chat 和 Cowork。

仍未确认

  • 同一个 Project 内，Chat 记忆与 Cowork 记忆是否完全打通——官方文档未明说。
  • Cowork 项目数据是否已完成从本地存储到云端同步的迁移（两篇官方文档口径不一致，以桌面版实际表现为准）。
